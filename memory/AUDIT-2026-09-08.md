## Findings by Category

### 🔴 Critical (Would Have Caused Crashes)

| # | File | Issue | Fix |
|---|------|-------|-----|
| 1 | `js/auth.js:37` | `getSessionUser()` called `user.id` without null-checking `getCurrentUser()` first — would crash on unauthenticated page load | Added null guard: `if (!user) return null;` |
| 2 | `js/admin.js:227` | `deactivateAccount(userId, userName)` — HTML passes `onclick="deactivateAccount('${u.id}', '${name}')"` but function expected `(userId, userName)`. With the old order, `userName` was treated as `userId`, causing SQL to target wrong user | Reordered params: `deactivateAccount(userId, userName)` now matches HTML calls |
| 3 | `js/dashboard.js:180` | `initPage_dashboard` called `getProducts()` and `getPendingChangeRequests()` but these were not imported in the inline script scope | Added proper imports inside the function |
| 4 | `js/admin.js:126` | `viewGovernmentId()` called `getSignedUrl()` without try/catch — would crash with unhandled promise rejection if bucket doesn't exist | Wrapped in try/catch with user-friendly toast |

### 🟠 High (Data Integrity / Logic Errors)

| # | File | Issue | Fix |
|---|------|-------|-----|
| 5 | `supabase/schema.sql:115-128` | `handle_new_user()` trigger did `INSERT` into `profiles` — but signup form also inserts a profile for the same `id`. This caused `duplicate key value violates unique constraint "profiles_pkey"` | Changed to `INSERT ... ON CONFLICT (id) DO NOTHING` |
| 6 | `supabase/schema.sql:140-157` | `notify_new_seller()` used `sp.profiles.full_name` — but `seller_profiles` has no FK to `profiles`, only to `auth.users`. The JOIN was wrong | Fixed to `join profiles up on up.id = new.user_id` |
| 7 | `supabase/schema.sql:286-318` | Storage RLS policies used `split_part(path, '/', 1)` — `path` column doesn't exist in `storage.objects`. Column is `name`. Also used segment 1 but path is `sellers/{uuid}/...` so UUID is in segment 2 | Changed to `split_part(name, '/', 2)` |
| 8 | `js/supabase.js:62` | `getAllSellerProfiles()` used `profiles!seller_profiles_user_id_fkey(...)` — but the FK constraint name wasn't guaranteed to match. Supabase auto-generates FK names, but using `!` syntax requires exact match | Changed to `profiles:user_id(...)` alias syntax which is more reliable |
| 9 | `js/supabase.js:95` | `getAllPendingChangeRequests()` used 3-table nested join `seller_profiles!seller_change_requests_seller_id_fkey(tier, user_id, profiles!seller_profiles_user_id_fkey(...))` — fragile with auto-generated FK names | Rewrote with explicit FK constraint names matching schema |

## Architecture Verification

### Data Flow: Buyer Registration
```
signup.html → signUp(email, pw, {full_name})
  → Supabase Auth creates user
  → Trigger handle_new_user() inserts basic profile (ON CONFLICT DO NOTHING)
  → Form inserts full profile (upsert onConflict:'id')
  → toast + redirect to login
✅ Verified
```

### Data Flow: Seller Registration
```
signup.html → signUp(email, pw, {full_name, role:'seller'})
  → Supabase Auth creates user
  → Form upserts profile with role='seller'
  → Upload government ID to 'government-ids' bucket
  → Insert seller_profile with approval_status='pending'
  → Trigger notify_new_seller() creates admin notifications
  → toast + redirect to login
✅ Verified
```

### Data Flow: Seller Edit (Critical Workflow)
```
dashboard.html#business → form submit
  → submitSellerChangeRequest(userId, changes)
  → Fetches current seller_profile for old values
  → Inserts seller_change_requests with changes, old_values, new_values, status='pending'
  → Updates seller_profiles.approval_status = 'pending-review'
  → Creates admin notification
  → Tries to send email via edge function (non-critical if fails)
  → toast('Changes submitted for admin review')
✅ Verified — approved data preserved, pending changes separate
```

### Data Flow: Admin Approval
```
admin.html → click Approve
  → approveSeller(userId)
  → Updates seller_profiles.approval_status = 'approved'
  → Creates notification for seller
  → toast + reload list
✅ Verified
```

### Data Flow: Admin Change Review
```
admin.html → click Approve on change request
  → adminApproveChange(requestId, sellerId)
  → applySellerChanges() in profile.js
  → Fetches change request, gets new_values
  → Updates seller_profiles with new_values
  → Marks change request as 'approved'
  → Resets seller_profiles.approval_status to 'approved'
  → Creates activity log
  → toast + reload
✅ Verified — old data never overwritten before approval
```
